# boatrace_saas

ボートレースの公開データを収集・分析するデータ基盤。
半自動運用を前提に、人の介在を「異常が出たときだけ」に寄せている。

## 現在の状態

**データ収集は動作する。予測モデルはまだ市場オッズに負けている。**

パーサーは全項目について実データで動作確認済み。一方、予測モデルは
バックテストで市場オッズに負けており、期待値（EV）は理論上の優位性を示さない。
`scraper/scoring.py` の `CALIBRATED = False` がその状態を表している。

**2026-09-07 から、AI予想は較正の完了を待たずに公開している。** レース詳細に
予測1着率と3連単の推奨買い目を出し、免責事項を添えてある。ただし公開する確率は
モデル単独ではなく、市場オッズへ引き戻した混合（`scraper/scoring.py` の
`BLEND_WEIGHT`）である。モデル単独だと三連単の的中目で市場に
+0.3319 ± 0.0297 負けており、推奨買い目のEVが軒並み2〜5倍になっていたため。
重みの根拠は `py -3 experiment.py` の `trifecta_blend_check` が出す。`CALIBRATED` は
公開の門番ではなく、その予測を出したモデルが市場を上回っていたかの記録として
`predictions.calibrated` に残るだけになった。モデルの改善は並行して進める。

## 構成

```
scraper/
  session.py      HTTP共通。2秒のレート制限。過去日ページは cache/ に保存
  schedule.py     開催場一覧、締切予定時刻
  racelist.py     出走表（選手・級別・勝率・モーター・ST）
  beforeinfo.py   直前情報（展示タイム・チルト・気象）
  odds.py         三連単オッズ、そこから逆算した市場勝率
  result.py       確定着順・決まり手・払戻金
  scoring.py      予測勝率と期待値
jobs.py           GitHub Actionsから呼ぶ収集ジョブ
pipeline.py       手動でその日を一括取得（デバッグ用）
backtest.py       過去データの収集・評価・較正
experiment.py     モデル候補を対応のある比較で検証する
db/
  schema.sql      Supabaseスキーマ。オッズの推移は odds_series ビューを使う
  loader.py       JSONをSupabaseへUPSERT
web/              画面（Next.js）
```

## 画面

```
cd web
npm install
npm run dev
```

`web/lib/data.ts` の3関数がデータ取得を引き受ける。Supabaseの環境変数が
設定されていればDBを、無ければ収集ジョブが書く `output/<日付>.json` を読む。
本番はDB、手元はファイル、という使い分けを画面側に意識させない。
保存先を変えてもこの3関数だけで済み、`web/app/` 以下は触らない。

見せているもの:

- **市場勝率** — 三連単オッズから逆算した各艇の1着確率
- **コース標準との差** — 市場評価が全国平均のコース別1着率からどちらに
  どれだけ振れているか。1号艇が左（赤）に振れているレースは、
  標準どおりに決まりにくいと市場が見ている。公式サイトには無い視点
- **展示タイム** — 6艇が0.1秒程度の幅に収まるため、棒グラフではなく
  共通軸のドットプロットで描く。棒にすると基準を任意にずらすことになり、
  わずかな差が何倍もの長さの差に見えて誤読を招く
- **出走表** — 級別・勝率・モーター・ST・展示を一覧で比較

配色は艇色（1白2黒3赤4青5黄6緑）を艇番バッジの識別チップに限定し、
チャートの系列色には使っていない。白と黒は彩度・明度の基準を構造的に
満たせず、満たすよう調整すると競技上の識別が壊れるため。

## 日々の運用（想定5分）

平常時は何もしない。GitHub Actionsが以下を自動実行する。

| ジョブ | 起動(JST) | 内容 | 所要 |
|---|---|---|---|
| `morning` | 09:00 | 全レースの出走表 | 約34分 |
| `prerace-loop` | 09:30 / 13:30 / 17:30 | 締切30分以内のレースの直前情報とオッズを20分ごとに繰り返す | 次の起動時刻まで |
| `results` | 22:00 | 確定結果 | 約31分 |

所要時間はCIでの実測に基づく。手元（日本）で走らせると1/5程度で済む。

### 起動はcronに頼らず、自分で次を予約する

**GitHubのスケジュールは1日2〜3回しか発火せず、しかも発火するのは
`morning` と `results` の枠だけだった。** `prerace-loop` に割り当てた3本は
3日間で一度も発火していない。cronの本数を増やしても発火数は増えない。

そこで、確実に発火している1回を起点にして、各実行の最後に次の
`prerace-loop` を `workflow_dispatch` で予約する。cronへの依存は
「1日どこかで1回発火すること」だけになる。1本あたり5時間20分走り、
21:40 まで数珠つなぎで日中を覆う。

これには Actions の書き込み権限を持つ PAT が要る。`GITHUB_TOKEN` では
workflow_dispatch を起こせない（無限再帰を防ぐためのGitHubの仕様）。

1. GitHub の Settings > Developer settings > Personal access tokens >
   Fine-grained tokens で発行する。
   - Repository access: このリポジトリだけ
   - Repository permissions: **Actions を Read and write**
2. リポジトリのシークレット `DISPATCH_TOKEN` に入れる。

**未設定でも壊れない。** その場合は予約せず、従来どおりcron頼みになる。

予約の暴走を防ぐ歯止めを3つ置いている。連鎖する仕組みは、失敗が高速で
繰り返されると実行時間と公式サイトへの負荷を際限なく使うため。

- 開催時間帯（09:00〜21:40）の外では予約しない
- `results` からは予約しない
- **10分未満で終わった実行からは予約しない。** すぐ落ちる状態で連鎖すると、
  1分ごとに起動を繰り返すことになる

トークンが期限切れになると予約に失敗し、その日の残りが黙って収集されない
まま終わる。そうならないよう、予約の失敗は必ずジョブの失敗として通知させて
いる。**通知が来たらまずトークンの期限を疑うこと。**

**現在のトークンの有効期限は 2026年12月3日。** 切れる前に発行し直して
`DISPATCH_TOKEN` を更新する。更新を忘れても収集が静かに止まることはなく、
予約に失敗した時点で通知が飛ぶ。

**`prerace` を毎時のcronで回す形はやめている。** GitHubのスケジュールは
保証されず、実測では30分毎に設定しても1日1〜2回しか発火せず、しかも
1〜4時間ずれた。締切前の情報は発火時刻の精度に全面的に依存するため、
この方式では稼働2日でオッズが取れたのが10レースだけという結果になった。

代わりに `prerace-loop` を1日3回起動し、その中でループさせている。
発火回数に依存しなくなるうえ、窓を30分と狭く取れるので締切に近い、
つまり市場の最終的な評価に近いオッズが取れる。3本に分けているのは
GitHubの1ジョブあたりの上限が6時間だからで、1本が間引かれても
残りの時間帯は影響を受けない。

ループは各パスの直後にSupabaseへ取り込む。4時間走り切ってから
まとめて入れる形だと、その間画面が更新されず、途中で異常終了した場合に
その日の収集がまるごと失われるため。

対象を「締切が近いレースだけ」に絞っているのは、公式サイトへの負荷を
抑えるため。GitHubのランナーは US リージョンにあり boatrace.jp まで
1リクエスト約12秒かかる（日本から実行した場合の約5倍）。

リポジトリはPublicにしている。Public であれば Actions の実行時間が
無制限無料になり、この所要時間が問題にならないため。収集したデータは
リポジトリに入れず Supabase に置くので、公開されるのはコードと
テスト用HTMLだけになる。

**人が動くのは通知が来たときだけ。** 失敗時のみWebhookに通知が飛ぶ。
何も通知が来なければ正常。

取得したデータはリポジトリにコミットせず、Supabaseへ入れる。
公式サイトのデータを再配布しないため、また毎日数百KBずつ履歴が
膨らむのを避けるため。DBを設定するまでは、各実行の
アーティファクト（7日保持）で何が取れたかを確認できる。

### 異常時の見方

`prerace-loop` は各パスの後に健全性チェックを行う。欠損が出ても
その場では止めず、ループを最後まで走らせてから異常終了する。途中で
落とすとその日の残り時間の収集がすべて失われるため。データは各パスで
取り込み済みなので、異常終了しても失われない。

確認すべき順序は次の通り。

1. **開催場が0場** — `get_active_venues` が空を返している。
   **ボートレースに開催0の日は無いので、これは「今日は何も無い」ではなく
   パーサーが壊れたことの同義語**と読む。トップページの `jcd=` リンクか、
   フォールバック先の月間スケジュールの体裁が変わった可能性が高い。
   `morning` `results` `prerace` はこの状態で異常終了する。
2. **overround異常** — 正常値は約1.334（＝1/0.75、控除率25%と整合）。
   この値が崩れているときはオッズの取りこぼし、つまり
   **サイトのHTML構造が変わってパーサーが壊れた**可能性が高い。
3. **出走表の値がありえない範囲** — 列がずれている。勝率の欄に3連対率が
   入る（10点満点を超える）、平均STの欄に勝率が入る（1秒を超える）など。
   **6艇すべてに同じ異常が出ていれば、ほぼ確実に列ずれ。**
   `morning` と `prerace` の両方で検査している。
4. **出走表が6艇でない** — 中止・欠場か、パーサーの破損。
5. **オッズ未取得** — 開催中止か、締切時刻の判定ずれ。

**「開催場が0場」を検査していなかった時期がある。** そのときは全ジョブが
「0レース取得完了」と印字して正常終了し、通知は失敗時にしか飛ばないため
何も鳴らず、その日の収集がまるごと失われても気づけなかった。しかも
`prerace-loop` は規定時刻まで走り切るので、10分未満で終わった実行からは
予約しないという歯止めも反応せず、1日中ランナーを回して何も集めない状態が
静かに続く形になっていた。**「何も通知が来なければ正常」という運用前提は、
何も取れていない状態が必ず失敗になることに依存している。**

なお「締切が近いレースが0」は正常で、時間帯によっては当然そうなる。
0場とは区別してあり、こちらでは落とさない。

手元で再現するには次を実行する。ループではなく1回だけ走る。

```
py -3 jobs.py prerace --window 40
```

ループそのものを手元で試すなら終了時刻を近くに置く。

```
py -3 jobs.py prerace-loop --until 21:40 --interval 20 --window 30
```

## テスト

```
py -3 -m unittest discover -s tests
```

`tests/fixtures/` に置いた実際のHTMLで各パーサーを検証する。
ネットワークに出ないので即座に走る。パーサーを触ったら必ず流すこと。

検証しているのは主に「列のずれ」で、これが最も起きやすく最も気づきにくい。
氏名欄が数字になっていないか、勝率が10点満点の範囲か、平均STが1秒未満か、
三連単が120通り揃っているか、といった値域の妥当性を見ている。

**このテストはサイト側のHTML変更を検知しない。** フィクスチャは固定なので、
サイトが変わってもテストは通り続ける。そちらは実行時の健全性チェック
（特にオッズのoverroundが約1.334から外れないか）が担っている。

### オッズの推移を読むときは `odds_series` を使う

`odds_snapshots` は追記専用の時系列だが、**生のまま読んではいけない。**
`prerace-loop` は各パスの直後に日次ファイル「全体」を取り込むので、一度取得した
レースが以降の全パスで再投入される。`loader` の `_insert_odds` が直前と同じ内容を
弾くようになる前に積まれた行が残っており、実測で2026-09-03に**1レース13件、
overroundが全部同じ値のまま9時間にわたる**という並びができている。
`captured_at` が実際の取得時刻を表していないので、そのまま推移として読むと
「9時間動かなかった」という嘘になる。

`odds_series` ビューが、内容が動いた瞬間だけに畳んだものを返す。
**行は消していない。** 削除は不可逆で、各レースの最初の1件は本物だからである。

```
生のスナップショット 435件 → 畳んだ後 189件（246件が重複）
```

**畳んだ結果、推移が2点以上残るのは31レースしかない。** 生データでは54レースに
見えるが、その差23レースは事故の残骸である。現在の収集設定（締切30分の窓・
20分間隔）では1レースあたり最大2回しか取りに行かず、値が動いていなければ
重複防御が正しく弾くので、実質1点しか積まれない。**オッズの推移を資産として
使いたいなら、待つのではなく収集設計を変える必要がある。** それは公式サイトへの
負荷と実行時間に直接効くトレードオフになる。

## 較正の進め方

モデルが市場オッズを上回らない限り、この基盤に商品価値はない。
較正は以下の順で回す。

```
py -3 backtest.py collect 20260801 20260831   # 過去データを集める（時間がかかる）
py -3 backtest.py enrich                      # 各行に直前情報を後付けする
py -3 experiment.py                           # 候補の採否を検証側で判断する
py -3 backtest.py eval                        # 配備前の健全性確認
py -3 backtest.py calibrate                   # 配備用に全データで係数を取り直す
```

`collect` は出走表・オッズ・結果しか取らない。展示タイムと気象は別ページに
あるため `enrich` で後から足す。予測モデルはこの当日情報に依存しているので、
`enrich` を通していないデータで評価すると実力を過小に見積もる。

過去日のページは `cache/` に保存されるため、`eval` と `calibrate` は
サイトを叩き直さずに何度でも走る。パラメータをいじりながら
評価を回す作業がスクレイピング待ちにならない。

**判断基準は LogLoss と Brier が市場オッズを下回ること。** 的中率だけを
見てはいけない。的中率は「1号艇を常に選ぶ」だけでも約50%出るうえ、
予測の自信度が正しいかを何も語らない。

### 「較正してから再評価」をしてはならない

**以前ここには `eval` → `calibrate` → `eval` と書いてあった。この順は嘘の
改善を出す。** `calibrate` は全データの勝者から場別コース勝率を作り、
`eval` はその同じデータを採点していた。自分で作った答えで答え合わせを
することになる。

実測すると、検証612レースでの見かけの改善は **LogLoss で 0.0409** だった。
モデルが市場オッズに負けている差は約0.098なので、**埋めようとしている差の
4割が自己成就だった**ことになる。

いまは `eval` が日付で学習と検証に分け、基準率を学習側だけから推定して
検証側だけを採点する。`calibrate` は配備用で、全データで取り直すのが正しい。
判断には使わない。

**それでも `eval` の数字は楽観側に寄っている。** `scraper/scoring.py` の
`LOGIT_WEIGHTS` は全データで当てはめた係数なので、検証側にもその情報が
入っている。**候補の採否は `experiment.py` の対応のある比較でのみ決めること。**
`eval` は配備前に壊れていないかを見るためのものと考える。

### 予測モデルの現在地

条件付きロジット（レース内ソフトマックス）で、コース別1着率を土台に
レース内で中心化した特徴量の重み付き和で補正する。
**検証1,212レース（全2,304レース、2026-08-25〜09-08）での成績。**

| 予測器 | LogLoss | Brier | 的中率 |
|---|---|---|---|
| 市場オッズ | 1.1352 | 0.5568 | 59.3% |
| 配備モデル（ロジット+当日全部） | 1.1902 | 0.5778 | 58.5% |
| 乗算モデル（手で決めた重み、+級別 +当地） | 1.2196 | 0.5894 | 56.8% |
| コース基準のみ | 1.3632 | 0.6501 | 54.8% |

**市場オッズとの差は 0.054 ± 0.010。まだ負けている。**

**2026-09-09、全2,304レースで係数を取り直して配備した**（`LOGIT_WEIGHTS`）。
同時に `wind_inner` と `in2_rate_all` を外している。どちらも外して差が出ず
（+0.0001 ± 0.0002 と -0.0001 ± 0.0001、12分割すべて誤差の範囲）、しかも
`wind_inner` は当てはめ直すと符号が正へ反転して「風が内枠を助ける」形になる。
信号ではなくノイズだった。**誤差に埋もれるなら単純なほうを採る。**

旧係数（1,236レースで当てはめ）との比較は検証1,212レースで
**-0.0046 ± 0.0016**。ただし新係数はこの検証データも見て当てはめているので、
この数字は新側に有利に出ている。配備は全データで取り直すという手順どおりで、
偏りを避けられない部分でもある。判断そのものは分割した検証で済ませてある。

係数を取り直したら `db/loader.py` の `MODEL_VERSION` を必ず変えること。
`model_performance` はこの名前で成績をまとめるので、同じ名前のまま中身を
変えると別のモデルの予測が1つの成績に混ざる。今回は `logit-2026-09`。

**`backtest.py calibrate` が書き出す `scraper/course_rates.json` は配備していない。**
このファイルを置くとオフセットが場別の基準率に変わるが、`LOGIT_WEIGHTS` は
固定の `COURSE_BASE` を土台に当てはめた係数なので、検証したモデルと配備される
モデルが別物になる。場別の基準率を使うなら、その基準率を土台にして係数を
当てはめ直し、検証もやり直すこと。今は手を付けていない。

ロジット化と当日情報を入れた効果は、乗算モデルに対して
**-0.0294 ± 0.0064**。分割位置を12通りに変えても符号は一貫して負で、
うち7つで標準誤差の2倍を超える。**効いたのは形ではなく情報だった。**
手で決めた重みを最尤で当てはめ直しただけでは差は小さく、展示タイム・
チルト・気象という当日の情報を入れて初めて明確な改善になる。

### 節間成績と直近の調子は、データを増やしても効かなかった

**以前ここには「効かない原因はデータ量だと考えられる」と書いてあった。
2,304レース（15日）に増やして測り直したところ、それは否定された。**

カバレッジは狙いどおり改善している。1艇あたりの過去走は中央値4走
（以前は3走）、過去走ゼロの艇は16.5%から**10.5%**へ、4走の窓を満たす艇は
40%から**58.4%**へ。それでも効果は出ない。

```
主分割         -0.0020 ± 0.0020   誤差の範囲
12分割の内訳    悪化2 / 誤差の範囲10
```

節が短いからではなく、**出走表の期別勝率と当日の展示タイムが同じ情報を
既に持っている**のだと考えられる。直近N走の平均STや平均着順を足しても、
そこに新しい情報がほとんど無い。窓幅を2/3/4/6/10走と変えても、広げるほど
効果が小さくなる挙動は変わらなかった。

再挑戦するなら、直近の走りそのものではなく「同じモーターが節の中で
どう変わったか」のように、既存の特徴量が持っていない軸を探すこと。

### 部品交換とプロペラは、まだ測れていない

直前情報ページの部品交換とプロペラ交換を特徴量にして測った
（`backtest.py backfill-machine` が後付けする）。

```
主分割         +0.0004 ± 0.0008   誤差の範囲（符号は悪化側）
観測           部品交換 713艇 (5.2%) / プロペラ新品 72艇 (0.5%)
```

**これは「効かない」と言い切れる結果ではない。** 延べ13,824艇のうち交換が
5.2%、プロペラ新品に至っては72件しかなく、検出できる効果の下限が大きい。
「情報が無いのか、情報に価値が無いのか」を区別できていない側なので、
データが数倍になってから再判定する。

### スタート展示のSTは有望（ただしまだ採用しない）

展示のSTと、枠番から何コース内に入ったか（前づけ）を特徴量にして測った。

```
主分割         -0.0017 ± 0.0035   誤差の範囲
12分割の内訳    すべて符号が負（改善方向）。2SEを超えたのは1つ
              20260827 -0.0025 → 20260905 -0.0073 → 20260906 -0.0105 ± 0.0047
```

**学習データが増えるほど効果が大きくなる。** 履歴特徴量が「窓を広げるほど
小さくなる（ノイズを拾っている）」挙動だったのと正反対で、信号がある側の
振る舞いに見える。ただし基準（差が標準誤差の2倍）を満たすのは1分割だけなので
採用はしない。**次にデータが増えたとき、最初に見る候補がこれ。**

### 進入コースを枠番で代用している件

`scraper/scoring.py` は進入コースを枠番で代用している。実測では結果ページの
18.1%で両者が一致しない。スタート展示の進入なら締切前に分かるので
代わりに使えるが、**改善は控えめ**だった。

| 進入コースの推定 | 艇ごと一致 | 並び完全一致 |
|---|---|---|
| 枠番をコースとみなす（現行） | 91.1% | 81.5% |
| スタート展示の進入 | 94.3% | 86.9% |

艇単位では現行がすでに91.1%当たっており、展示が回収するのは残り誤差の
約3分の1にすぎない。展示STと本番STの相関も r = 0.121 と弱く、展示が
前づけを示したとき本番も同じ並びだったのは58.1%しかない。
`scoring.py` の `actual_course` はこのために用意された分岐だが、
埋める価値があるかは未検証。

場別のコース勝率は縮小推定（`SHRINKAGE_K`）で全場平均に引き寄せている。
1場あたり12レース程度の観測で場の個性を語ると、偶然の偏りを
そのまま学習してしまうため。場別推定が意味を持つには
最低でも1000レース規模のデータが要る。

```
pip install -r requirements.txt
```

GitHub Actionsに設定するシークレット:

## デプロイ

公開先は boat-win.jp（Vercel）。手順は次のとおり。

1. **Supabaseプロジェクトを作る。** SQL Editorで `db/schema.sql` を実行する。
2. **収集ジョブにDBを教える。** Project Settings > Database の接続文字列を
   GitHubのシークレット `DATABASE_URL` に入れる。

   ```
   gh secret set DATABASE_URL
   ```

3. **Vercelにインポートする。** このとき **Root Directory に `web` を指定する**。
   リポジトリ直下には requirements.txt と .py があるため、既定のままだと
   VercelがPythonプロジェクトと誤検出してNext.jsとしてビルドされない。

   環境変数に `NEXT_PUBLIC_SUPABASE_URL` と `NEXT_PUBLIC_SUPABASE_ANON_KEY`
   を設定する（Supabaseの Project Settings > API の値。`web/.env.example` 参照）。
4. **ドメインを繋ぐ。** Vercelのドメイン設定で boat-win.jp を追加し、
   表示されるDNSレコードをレジストラ側に登録する。
5. **アクセス解析を有効にする。** Vercelのプロジェクトの Analytics タブで
   Web Analytics を有効にする。`web/app/layout.tsx` の `<Analytics />` は
   組み込み済みだが、**有効化するまで何も記録されない**（スクリプトの読み込みが
   404になるだけで、画面は壊れない）。

   cookie も localStorage も使わず、訪問者はリクエストから作るハッシュで
   数えられ、24時間で破棄される。**何を集めて何を集めないかは `/about` の
   「アクセス解析」に書いてある。道具や項目を変えたら、その記載も必ず直すこと。**

**Vercelでは環境変数の設定が必須。** 未設定だとローカルJSONを読もうとするが、
Vercel上に `output/` は存在しないため、画面には何も表示されない。

`service_role` キーをフロントに置かないこと。ブラウザに露出し、
RLSを迂回して誰でも書き込める状態になる。フロントは anon キーだけを使う。

### 表現に関する注意

有料サービスで的中率や収益性を訴求すると、景品表示法の優良誤認に
あたるおそれがある。実際に予想サイトへの措置命令が出ている領域なので、
**訴求軸は「勝てる」ではなく「データが見やすい」に置くこと。**
モデルが市場オッズを上回っていない現状では、なおさら期待値を
売り文句にしてはならない。

**AI予想と推奨買い目を画面に出しても、この線は変わらない。** 出しているのは
モデルの推定であって、的中や収益の約束ではない。予想エリアと
`/about#disclaimer` の免責事項は、その区別を明文にしたものなので消さないこと。

有料化する場合は特定商取引法に基づく表記も必要になる。
